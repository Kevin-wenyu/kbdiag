# 逐条打磨命令输出：从 status 开始

**状态**：active（2026-09-26 用户批准）

**背景**：v2.0.0-alpha.1 的 7 条命令测试是绿的，但用户看 status 时看不出参数有没有生效，也不知道 WARN 该在什么时候出现：输出没有回答工程师真正想问的问题。用户定的做法是一条一条打磨：先按 MECE 把场景列全，参数只从场景里推，用户确认输出草样后再实现。status 是第一条，它的输出形态会成为后面 6 条的模板。

## 1. 全工具约定（status 先定，后面各条照用）

| 约定 | 内容 |
|---|---|
| 级别 | **FAIL = 业务已经受影响**（例如连不上）；**WARN = 业务暂时没受影响，但不处理会出事**。只有不管应用怎么设计都算异常、而且有明确下一步的情况才报；像"连接数 80%"这种因应用而异的比例不报 |
| 阈值 | 只用客观线；没有客观线的只展示、不判定。没人会调的阈值不做成参数 |
| 文本输出给人看 | 结论和 finding 放在最前面；单行数据用"键 值"排版；大小、时长换成人能读的单位（`325 MB`、`3d 13h`）；各段按问题的先后排，不按 probe_id 字母序 |
| JSON 给脚本 | 保留原始单位（字节、秒），字段名不变 |

套用到其他命令时要重新核对级别：`slots` 不活跃、长事务 1800 秒、2PC 900 秒现在报 FAIL，按上面的定义应该是 WARN。打磨到那几条时再改。

## 2. status 的场景表（MECE）

status 回答"刚登上这个实例，它是谁、现在基本盘稳不稳"，按问题分成 4 类，各类之间不重叠：

| 类 | 工程师想问 | 输出里对应的内容 | 现状 |
|---|---|---|---|
| A 身份 | A1 我连对实例了吗 | 短版本号、数据目录、端口 | 版本号过长会被截断，缺端口 |
| B 角色 | B1 主库还是备库 | 首行的 role | 已有 |
| | B2（主库）挂了哪些备库，各自在不在同步 | 每个备库一行：名字、地址、状态、同步方式 | 只有一个数字 |
| | B3（备库）上游是谁，在不在收 WAL | 接收状态、上游地址、上一条消息是几秒前 | 没有；slots 的建议只能绕去 sessions |
| C 可用性 | C1 最近重启过吗 | 启动时间 + 已运行多久 | 已有，但给的是秒数 |
| | C2 业务还能连进来吗 | 已用 / 可用（可用 = max_connections − 超级用户保留） | 已有，但需要自己算 |
| D 容量 | D1 各库多大 | 按大小降序，附总量 | 已有，但给的是字节、按名字排 |
| | D2 磁盘还剩多少 | 数据目录所在文件系统的已用 / 总量 | 没有（待决定 1） |

**不在 status 里**（给出指向）：谁占的连接 → `sessions`；锁 → `locks`；复制延迟数值和复制槽 → `slots`（延迟放 v0.2）；在等什么 → `waits`。

**判定**：只有两条。
- `inst.connections` **FAIL**：已用 ≥ 可用，普通用户已经连不上。
- `inst.upstream` **WARN**（备库）：没有 WAL 接收进程，或状态不是 `streaming`。备库不收 WAL 不影响当前业务，但主库一挂就没有可切换的备库。

删除：80% 的 WARN，以及 `--conn-warn`、`--conn-fail` 两个参数。

**参数**：status 没有自己的参数，只用全局的连接参数和 `--json`。上面每个场景都不需要过滤或调整。
