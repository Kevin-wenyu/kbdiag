# kbdiag 2.0 测试方案

**状态**：pending approval
**日期**：2026-09-23
**要解决的问题**：旧版测试只证明了"命令能跑"，没证明"诊断对不对"。新方案的每一层测试都要回答：**如果这里有 bug，哪条测试会红？**

---

## 1. 测试分层总览

架构三段（见 02 §5）决定了测试分层——每层只测它负责的事，不越界：

| 层 | 测什么 | 不测什么 | 在哪跑 | 速度 |
|---|---|---|---|---|
| L1 规则单测 | `rule` 包：给定数据 → 应出哪些 finding、什么级别 | SQL 对不对 | Mac 本地 / CI | 秒级 |
| L2 渲染与契约 | `report` 包：text/json 输出、退出码、stdout/stderr 分离 | 业务判断 | Mac 本地 / CI | 秒级 |
| L3 Probe 契约 | 每条 probe 在真实 KES 上能跑、类型能 Scan、不超时、在备库/无 repmgr 下行为正确；**并在已知夹具上断言取值**（建已知大小的表、开已知 pid 的 idle 事务，断言 probe 返回的就是这些值）——KES 的语义怪癖（布尔、空串即 NULL、interval 格式）只有这一层能抓到 | 判断逻辑 | Lima VM | 分钟级 |
| L4 场景测试 | DS-01~24：注入真实故障 → 断言 finding 指向被注入的对象 | — | Lima VM | 分钟级 |
| L5 降级矩阵 | 单机/主备 × 主库/备库 × 本地/远程 × 权限不足/连不上/超时 | — | Lima VM | 分钟级 |
| L6 用户验收 | 用户本人按验收步骤操作确认 | — | 用户 | — |

**不使用 mock 数据库驱动**：mock 出来的只是"我以为数据库会返回什么"，这正是旧版测试不可信的来源。判定逻辑靠 L1（纯数据），SQL 正确性靠 L3/L4（真数据库），中间没有 mock 层。

## 2. L1 规则单测：怎么写

**形式**：Go 表驱动测试，一个 rule 一张表。每张表必须包含以下几类用例（暴力测试原则），缺一类 code review 不放行：

| 类别 | 示例（以连接数规则为例） |
|---|---|
| 正常/阴性 | 50/100 → 无 finding |
| 阈值边界 | 69/100、70/100、71/100；89、90、91 |
| 零与空 | `max_connections=0`（除零）、活跃会话列表为空 |
| 空值 | `application_name` 为 NULL、`query_start` 为 NULL（idle 会话） |
| 极值 | 10 万个会话（截断提示是否出现，GAP-4）；xid age 接近 2^31 |
| 非法值 | 负数时长（时钟回拨）、未知的 `state` 字符串 |
| 语义对照 | DS-04 对照组：idle-in-txn 但持排他锁 → **不得**标记为可安全终止 |
| 采集失败 | 输入 fact 的 status 为 `error`/`skipped` → 必须输出 UNKNOWN/SKIPPED，**不得**判 OK（防"没采到 = 没问题"） |

**辅助手段**：
- **Go 原生 fuzz**（`go test -fuzz`）用于解析类函数：版本字符串解析、大小单位换算、facts JSON 反序列化——要求任意输入不 panic
- **覆盖率门槛**：`rule` 包语句覆盖率 ≥ 90%，CI 卡住；覆盖率只是底线，不作为"测够了"的证据

## 3. L2 渲染与契约

- **Golden file**：每个 scenario 用一份固定 facts 渲染 text 和 json，与 `testdata/*.golden` 比对；改输出必须显式 `go test -update` 并在 diff 里被审
- **JSON 契约测试**：所有命令的 JSON 输出通过同一个 schema 校验；`finding.id` 列表与已发布清单比对，防止悄悄改名
- **退出码表测试**：verdict → exit code 映射单独一张表测
- **流分离**：断言结果只在 stdout、日志只在 stderr（旧版 `warn()` 写 stdout 的问题在这里被钉死）

## 4. L3/L4 集成与场景测试：怎么写

### 4.1 测试工具形态

测试代码本身也用 Go 写（`test/scenario/`，build tag `integration`），不再用 shell 编排：
- **测试程序和 kbdiag 一起交叉编译**（`go test -c` 产出测试二进制），scp 到 VM 上以 `kingbase` 用户运行，走本地 socket 免密——不需要在 Mac 上管 `system` 的密码和网络路径；Mac 端只负责编译、分发、收集结果
- 故障注入用 Go 开独立连接、在 goroutine 里持有事务/锁，比 `nohup ksql ... &` 可控：能精确知道注入会话的 pid、能确定地清理
- 被测对象是**真实的 kbdiag 二进制**（以子进程运行），解析其 JSON 输出——测的是用户实际拿到的东西，不是内部函数

### 4.2 每条场景测试的固定结构

```
Baseline 注入前先跑一次 kbdiag，记下已有的 finding（VM 上有与测试无关的背景状态，
         如 sys_stat_statements.track=none、repmgr 会话）
Setup    注入故障，记录"注入指纹"（pid、表名、锁模式、事务 xid）；
         同时放入诱饵（见 4.3）
Run      执行 kbdiag <命令> --format json
Assert   1. 与基线相比新增了指定 finding.id，且该 finding 的级别正确
            （断言单个 finding 的级别，不断言整体 verdict——它会被背景状态左右）
         2. finding.evidence 里包含注入指纹（证明报的是"我制造的那个问题"，不是巧合）
         3. 诱饵不在 evidence 里
Cleanup  终止注入会话、删除测试对象；无论测试成败都执行
```

第 2 条是和旧版的根本区别：旧版 `assert_contains "$out" "锁"`，新版断言 `evidence.blocker_pid == 注入会话的 pid`。断言只能引用 PRD §5 登记过的 evidence 字段；指纹字段缺失时判失败（不能出现零值 == 零值的假绿）。

### 4.3 防"假绿"机制（针对"测试不可信"）

| 机制 | 做法 |
|---|---|
| **阴性测试** | 每个 finding.id 配一条：不注入故障，断言该 finding **不出现**（抓"健康时误报"）。DS-01 是全局阴性对照 |
| **诱饵测试** | 注入真故障的同时，放一个"看起来像但不该被报"的会话——例如锁场景里放一个不阻塞任何人的 idle-in-txn 会话、DS-04 里放持排他锁的会话——断言诱饵不在 evidence 里或未被标"可安全终止"（抓"把所有会话都报出来"这类宽泛误报） |
| **变异抽查** | 发版前在 `rule` 包里人为改坏一个阈值比较（`>=` 改 `>`）或删掉一条规则，确认至少一条测试变红（可用 go-mutesting 之类工具，按需引入） |
| **对抗审查** | 新增测试时由两个独立 agent 互审：一个论证"这测试够了"、一个论证"这测试有漏洞"，分歧才交用户 |
| **禁止弱断言** | 场景测试中禁止只断言"exit 0"或"输出包含某字符串"；code review 检查项 |

## 5. 覆盖不到的场景：组合策略

有些场景在测试 VM 上无法真实、稳定、安全地复现。原则：**不假装测过**——每个场景在追溯矩阵里标明用了哪几种手段、哪部分没被真实验证。

| 手段 | 适用 | 做法 |
|---|---|---|
| **A. 阈值缩放** | 条件真实可造，但量级太大 | 通过 flag/环境变量把阈值调低，注入小规模的真实故障。例：DS-19 冻结年龄不可能真烧 10 亿 xid → 阈值调到 1000，真跑一批事务 |
| **B. Facts 回放**（v0.2 起） | 数据库/主机状态难以制造 | facts 文件**只能由 `--dump-facts` 从真实实例录制**，`--from-facts` 离线跑完整判定和渲染。例：DS-14 CPU 打满、DS-13 IO 延迟、现场客户问题快照。手写/改写的 facts 标为"合成"，本质上等同 mock：追溯矩阵里只能记"判定已测"，不能记"采集已测" |
| **C. 文件系统夹具** | OS 层采集 | `/proc/stat`、`/proc/diskstats`、`/proc/meminfo` 的真实快照存进 `testdata/proc/`，采集代码以可替换根目录读取，单测覆盖解析和计算 |
| **D. 半自动破坏性测试** | 需要停节点、断网，会影响其他测试 | 独立测试套件（build tag `destructive`），只在手动触发时跑，自带恢复脚本和前后健康检查。例：DS-21 `limactl stop kes-node2`（模拟崩溃）vs VM 内 iptables 丢包（模拟网络分区，VM 内 kevin 有 sudo）；DS-23 停 repmgrd；DS-24 制造不可 promote 条件 |
| **E. 人工 runbook** | 自动化成本远大于价值 | 写成验收步骤，由用户执行并记录结果。例：真实压测工具下的 CPU/IO 场景（stress-ng 在 VM 上跑） |

**组合原则**：同一场景尽量叠加两种以上手段覆盖不同环节——例如 DS-14 用 C 验证 `/proc` 解析、B 验证判定规则、E 验证真实负载下端到端表现。任何一个环节都不靠 E 以外的手段时，追溯矩阵里明确标注"仅人工验证"。

### 5.1 初版覆盖规划（24 个场景）

| 场景 | 主要手段 | 备注 |
|---|---|---|
| DS-01~02, 04~11, 15, 17, 18 | L4 真实注入 | 常规自动化 |
| DS-03 连接满 | L4 | 直接开 97 个普通用户连接（`max_connections=100`，留 3 个超级用户预留位）；不改 `max_connections`（要重启，且备库该值不能小于主库）；同时验证 N-03（满连接下 kbdiag 以 `system` 仍能连上） |
| DS-08 死锁 | L4 | 两个 goroutine 反序加锁，确定性制造 |
| DS-09 DDL 被阻塞 | L4 | 额外验证 N-02 的 `lock_timeout`：有 AccessExclusive 排队时，锁族照常出结果，需要表锁的 probe 进 `skipped` 而不是整条命令超时 |
| DS-12 缓存命中 | L4 + B | 累计值 vs 当前值要靠两次采集差值，真实环境难控，判定规则靠回放 |
| DS-13/14 IO/CPU | B + C + E | 典型"组合覆盖" |
| DS-16 WAL 增长 | L4 + A | 归档失败可通过改 `archive_command` 为失败命令真实制造 |
| DS-19 冻结 | A + L1 极值 | |
| DS-20 复制延迟 | L4 | 在备库用 `sys_wal_replay_pause()`（VM 已确认存在）暂停回放制造 |
| DS-21~24 HA | D | 破坏性套件，手动触发 |

## 6. 追溯矩阵（贯穿需求 → 实现 → 测试）

维护一张 `docs/rewrite/traceability.md`（随开发增量补），每行：

```
DS 编号 | 场景族/子命令 | finding.id | rule 函数 | L1 用例 | L4 场景测试 | 其他手段(A-E) | 未覆盖说明
```

**用途**：
- 发版门槛：MVP 范围内每行的 L1 和 L4（或已声明的替代手段）列不能为空
- 矩阵分两张表：场景表（DS-*）+ 需求表（F-*/N-*，如 F-01 socket 连接、F-02 角色识别、N-02 超时、N-03 满连接、N-04 只读），后者同样要填测试列
- 代码审查：新增 finding 没有对应 DS 行 → 违反"场景为王"原则，打回

## 7. 运行方式

| 命令 | 内容 | 何时跑 |
|---|---|---|
| `make test` | L1 + L2（含 fuzz 短跑） | 每次提交前（pre-commit） |
| `make itest` | 交叉编译 → 部署到 VM → L3 + L4 + L5 | 每个功能切片完成时 |
| `make dtest` | D 类破坏性套件 | 手动，HA 功能开发时 |
| GitHub Actions | 只跑 `make test`（CI 里没有 KingbaseES，受许可限制） | push 时 |

**诚实声明**：L3~L5 依赖本地 Lima VM，不在 CI 里——这意味着"CI 绿"不等于"集成测试过"，发版记录必须附 `make itest` 的实跑结果。

## 8. 验收（L6）

按验收纪律，每个版本发布前由我产出《验收步骤》文档（每个 DS 场景：怎么制造 → 敲什么命令 → 应该看到什么），**由你本人在 VM 上照着走一遍**，而不是以自动化测试结果代替验收。
