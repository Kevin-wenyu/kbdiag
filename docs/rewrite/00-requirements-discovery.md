## 案例 1：嘉实基金 insert 偶发 34s（2026-09-08）

**原始材料**：`~/Downloads/嘉实基金数据库故障分析报告20260917.docx`（麒麟 V10 + 鲲鹏 920）

**经过**：平时 ms 级的 insert，50 个并发同时卡了 34s，应用侧 30s 超时断开。开发第二天来问。排查依次用了：数据库日志（推出发起/提交时间）→ KWR（该语句最长 34s、等待占比 55%、`buffer_content`）→ OS IO（100%，同时段有 checkpoint）→ WAL 解析（7 个事务反复写 FSM FPI 后各做一次叶子页分裂，其余 43 个事务在分裂后集中插入、13.77ms 内集中提交）→ 读源码推理。

**结论**：根因没能坐实。报告原话："尚无现场持锁者、等待者和 buffer 标识直接证明"。

**补充假设（待验证）**：
- PG12 的 B-tree 删除页在 VACUUM 时就进了 FSM，但要等 xmin 视界推过之后才能复用
- 分裂时 `_bt_getbuf` 逐个取 FSM 候选页，先清掉再检查能不能复用，检查不过就换下一个；checksums 打开时，每次清 FSM 都产生一次 FPI
- 这与报告里"500+ 个 FSM 页全部不能复用、大量 FSM WAL"吻合
- 所以可能的真正诱因是：索引键单调递增（`sub_update_time`）+ 删除页多 + **当时有东西压住了 xmin 视界**（长事务、复制槽、备库 `hot_standby_feedback`、2PC）

**对需求的启示**：
1. 快照式实时诊断在这个案例里完全帮不上：故障已经过去，而且只持续了 34 秒
2. 最缺的是**出事时的会话级证据**；KSH 本来能提供，但没开
3. 深度要有边界：WAL 解析加源码推理是内核研发的活；kbdiag 该做的是把证据收全、把容易被漏掉的关联点出来（单调键 + 删除页 + 视界持有者）、给出排查方向
4. 由此得到"按时间"分三个模式的构想：**事前**（可观测性就绪检查 + 结构性风险扫描）/ **事中**（实时诊断）/ **事后**（按时间窗取证：KWR、日志切片、checkpoint、OS、LSN 范围）

**这个案例里，每个模式能拿到的证据**（KWR 开、KSH 不开的现实条件下）：

| 证据 | 事后可得？ | 来源 |
|---|---|---|
| 语句级耗时和等待占比 | ✅ | KWR |
| 时间窗内 OS 指标 | ✅（如果 `track_os=on`） | KWR |
| checkpoint、慢 SQL、锁等待日志 | ✅（取决于 `log_*` 配置） | 数据库日志 |
| 会话级等待、谁堵着谁 | ❌（要 KSH） | — |
| 出事时刻的 xmin 视界持有者 | ❌（除非 KWR 快照了活动会话，待核实） | — |
| 索引结构（单调键、删除页数） | ✅（结构变化慢，事后查的现状可以近似当时） | 系统表 + 索引检查函数 |

## 用户纠正：简单查询优先（2026-09-23）

> "查询也可以是单次的，就是看看有没有锁、会话信息等，可能只是看看，就知道了；但有时候是需要连环分析。我们先把简单的做了，再考虑深度的、复杂场景。"

- v0.1 只做简单的单次查询；上面"事前/事中/事后"三分法、案例 1 的深度分析，都作为 v0.1 之后的方向保留
- 计划见 `.omc/plans/2026-09-23-kbdiag-v2-phases.md`（r2）

## 待讨论

- 更多案例（最好是不同类型：锁堵塞、连接满、主备问题等），用来检验"事前/事中/事后"三分法是否站得住
- KSH 的开销有多大；kbdiag 是不是该在事前模式里建议客户打开它
