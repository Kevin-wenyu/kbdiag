# kbdiag 三维审计：命令重叠 / 文档 / 测试质量

**触发**：用户 2026-09-20 认为项目"失败"，指出四类问题——命令功能重叠、每个命令没有使用场景说明、文档没有例子、没有真正验证诊断质量的测试用例。本文档核实这些指控，给出证据和结论，不改代码。

**范围**：35 个顶层命令（34 个 `lib/cmd_*.sh` + `all`），README.md，`test/cases/*.sh`（37 个测试文件）。

---

## 一、命令重叠审计

方法：对每个命令的子命令 dispatch（`case "$subcmd" in ...`）做穷举提取，按子命令名做跨命令交叉比对，不是抽样。

### 1.1 子命令清单（穷举）

| 命令 | 子命令 |
|---|---|
| `perf` | `slow` `bloat` `vacuum` `index` `wait` `io` `wal` `top` |
| `idx` | `unused` `dup` `bloat` `missing` |
| `advisor` | `index` `vacuum` `params` `analyze` |
| `locks` | `wait`(默认) `hold` `deadlock` |
| `space` | `frag`（附加项，非独立子命令） |
| `cluster` | `ready`（附加项） |
| `check` | `--os`（附加项） |

### 1.2 重叠矩阵（同一概念，多个入口）

| 概念 | 出现位置 | 数量 | 严重度 |
|---|---|---|---|
| 表/索引膨胀（bloat/fragmentation） | `perf bloat`、`idx bloat`、`space frag` | 3 处 | **高**——三个命令用不同 SQL 各自判断同一件事，DS-17（验收文档）已确认阈值/口径不保证一致 |
| 索引健康 | `idx`（整个命令）、`perf index`、`advisor index` | 3 处 | **高**——`idx` 本身就是索引诊断的专门命令，`perf index`/`advisor index` 存在的理由从未在代码或文档里说明 |
| Vacuum 健康 | `perf vacuum`、`advisor vacuum` | 2 处 | **中**——`advisor vacuum` 是"给 SQL 建议"，`perf vacuum` 是"报状态"，勉强能自圆其说，但命名完全没有体现这个区分 |
| 等待事件/锁等待 | `wait`(顶层)、`perf wait`、`locks wait`(默认) | 3 处 | **高**——`wait` 和 `perf wait` 目前看代码是否完全同源未定（需要下一步逐行比对，本轮未做），`locks wait` 概念上是子集但共享"wait"这个词，DBA 无法从命令名判断该敲哪个 |

**结论**：4 组重叠，波及 `perf`/`idx`/`advisor`/`locks`/`wait`/`space` 共 6 个命令（占 35 个命令的 17%）。这不是"感觉重叠"，是可以用 `grep` 复现的具体子命令名冲突。**根因是三层命令哲学（看/查/断）只管了纵向分层，从未管过同层内命名与职责的横向去重**——每个命令是独立 tracer-bullet 交付的，没有一次"全局命令表评审"。

### 1.3 本轮未覆盖

`wait` vs `perf wait` 的实现是否逐行相同、`report`/`diagnose`/`advisor` 三个汇总类命令的职责边界，需要单独一轮代码级比对，本次审计只做了子命令名穷举，未深入每个重叠对的实现细节。

## 二、文档审计

### 2.1 README Command Reference（第 83-147 行）

穷举确认：35 个命令，Command Reference 是清一色的两列表格（命令名 | 一行描述），**零个**带示例输出，**零个**"什么时候用这个而不是那个"的场景说明。三个重叠簇（bloat/index/vacuum/wait）在表格里各自只有一行描述，读者无法从文档判断 `perf bloat` 和 `idx bloat` 该选哪个。

### 2.2 Quick Start（第 42-61 行）

有一个端到端例子（`kbdiag status` → `kbdiag check`），但只覆盖 2 个命令，其余 33 个命令没有任何用法示例。

### 2.3 结论

用户"文档没有例子"和"每个功能没有使用场景说明"两条指控，**逐字核实成立**，且和第一节的重叠问题互为因果——如果文档写清楚了"故障现象 A 用命令 X"，重叠的存在会立刻变得刺眼，倒逼命令整合；现状是文档和命令重叠互相掩护，用户很难靠文档发现自己该用哪个。

## 三、测试质量审计

**本轮未重复劳动**——`docs/dba-scenario-acceptance.md`（638 行，2026-09 早些时候产出，未提交）已经完成了这项工作，且质量远超本轮能重新做一遍的深度，结论直接引用：

- 现有 37 个 `test_*.sh` 是"执行+标签"断言（exit code / 子串匹配），不是"诊断质量"断言，逐条举证在该文档第一节。
- 已设计 24 个 DBA 故障场景（DS-01～DS-24），每条含 Setup/Expected Symptom/Evidence/Root Cause/Action/**False Positive**（专门验证"不该报的不报"），覆盖连接、锁、性能、vacuum、HA 五大类。
- 已识别 8 个真实能力缺口（GAP-1～GAP-8），比如锁阻塞链不自动拼接、Buffer Hit 是累计值未标注、Freeze 阈值两处不一致。

该文档卡在"场景设计阶段"——设计完了，没有变成 `test/cases/test_scenario_*.sh`，也没有提交。**这是本次三条指控里唯一已经有完整解决方案、只差"执行"这一步的一条。**

## 四、总体结论

用户的四条指控，逐条核实：

| 指控 | 核实结果 |
|---|---|
| 命令功能重叠 | **成立**，4 组重叠，6 个命令，有具体证据（§1.2） |
| 没有使用场景说明 | **成立**，README 零场景映射（§2.1） |
| 文档没有例子 | **成立**，35 个命令里 33 个零示例（§2.2） |
| 没有真正验证诊断质量的测试 | **成立**，但已有现成解决方案未执行（`dba-scenario-acceptance.md`） |

四条指控不是互相独立的四个小毛病，是同一个根因的四个表现：**项目从 2026-07 开始一直是"一个命令一个 tracer-bullet 交付"的节奏，从来没有做过一次全局收敛（命令表、文档结构、测试策略）**。每次交付单个命令时测试/文档都合格（这也是为什么之前的进度记录一直显示"回归全绿"），但从未有人跳出单命令视角看整体。

## 五、后续路径（供用户拍板，本文档不预设选哪条）
