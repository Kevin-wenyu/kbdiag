# kbdiag Capability-Gap Research: What `ora`/pg_profile/pgBadger/pgmetrics/pganalyze Do That kbdiag Doesn't

**Status**: research, not a spec. Feeds a follow-up planning conversation.
**Constraint baked in (Option C, already decided)**: kbdiag stays stateless, single-file (`dist/kbdiag`), pure-Shell, no daemon, no kbdiag-side persistent repository. A pg_profile-style metrics repository or a pgBadger-style rich HTML report generator is explicitly **out of scope this round** — see the one-line mention in the shortlist, not a design here.

---

## 1. Per-tool capability inventory

### 1.1 `ora` (local file: `~/Documents/oracle/ora`, 10,433 lines, POSIX shell)

A single monolithic shell script wrapping `sqlplus` calls, dispatched by first positional argument. Its own `-h` usage block (source: `~/Documents/oracle/ora:100-320`) enumerates ~90 subcommands. Categories relevant to this gap analysis:

- **Session/SQL introspection (real-time, no state needed)**: `execute`, `sessions`, `cursors`, `sharing <sql_id>`, `events`, `openv`, `plan`/`wplan`/`eplan`/`gplan`/`webplan` (EXPLAIN plan variants, with and without workarea/execution stats), `monitor`/`monitor_old` (live SQL Monitor wrapping `dbms_sqltune.report_sql_monitor()`), `sql_task` (progress/interrupt/history/report for `DBMS_SQL_TUNE` tasks) — source: `~/Documents/oracle/ora:106-256`.
- **Point-in-time historical sampling via Oracle's in-memory ASH buffer**: `ash <minutes_from_now> [duration]`, `ash_wait_graph`, `ash_sql <sql_id>` — all query `v$active_session_history` directly (source: `~/Documents/oracle/ora:637, 4187, 4213, 5710, 10102`). This is the single most relevant capability for this research: Oracle's `v$active_session_history` is a **database-maintained rolling circular buffer**, populated automatically every second by the instance itself — `ora` does zero sampling/state-keeping; it just queries a view.
- **Persistent-repository historical reporting (AWR)**: the entire `awr_*` family (`awr_dbtime`, `awr_sql_elaps_time_order`, `awr_plan`, `awr_top10_events`, etc., ~25 subcommands, source: `~/Documents/oracle/ora:261-299`) queries `dba_hist_*` / `wrm$`/`wri$` tables (source: `~/Documents/oracle/ora:6014-6762` region). This requires Oracle's **licensed, persistent AWR repository** — the exact thing already confirmed absent in KingbaseES's native catalog (per task background) and explicitly out of scope for kbdiag to rebuild itself.
- **Memory advisor graphs**: `pgaadv`/`sgaadv` (with `-s <snaptab>` diff mode), `pgaadvhist` — needs `v$pga_target_advice`/`v$db_cache_advice`, an Oracle-specific memory-advisor construct with no PostgreSQL/KingbaseES analog.
- **Fragmentation/top-N reports**: `tab_frag`, `index_frag`, `top_buffers_gets`, `top_executions`, `top_cpu_usage`, etc. (source: `~/Documents/oracle/ora:300-313`) — one-shot catalog queries, no state.
- **Repeat/poll wrapper**: `repeat <interval> <count|forever> <ora command>` (source: `~/Documents/oracle/ora:101-102`) — generic interval-repeat of any subcommand, no delta/trend computation between iterations.

Net read: `ora`'s deepest value (ASH, AWR) comes from Oracle's own database-side state, not from `ora` maintaining state. Where Oracle exposes a rolling buffer, `ora` is stateless too.

### 1.2 pg_profile (github.com/zubkov-andrei/pg_profile)

A PL/pgSQL **extension** that lives inside the target database. It is explicitly snapshot-based: a cron-scheduled job calls a snapshot function that reads `pg_stat_statements`, `pg_stat_kcache`, and the standard `pg_stat_*` catalog views, and persists the deltas into its own repository tables. Reports are generated by diffing two snapshot IDs (or two snapshot ranges for A/B comparison) and rendering an HTML report with top-SQL-by-metric tables, wait-event summaries, vacuum/IO stats, and object-growth trends. Supports cross-server/cross-cluster consolidated reporting from one repository. (Source: github.com/zubkov-andrei/pg_profile — README.md and doc/pg_profile.md.)

This is architecturally the closest analog to what Option C rules out for kbdiag: **the repository lives in the database, not in kbdiag**, which is worth noting precisely because it foreshadows section 3 below — KingbaseES already ships something in this shape (`sys_kwr`), just not built by kbdiag.

### 1.3 pgBadger (github.com/darold/pgbadger)

A standalone Perl script; **no daemon, no database connection required at all** — it parses PostgreSQL log files offline (syslog/csv/jsonlog/pgbouncer/rds-cloudwatch/etc., with gzip/bzip2/zstd support and SSH/HTTP/journalctl fetch modes) and renders a report. Report sections: slowest/most-frequent/most-time-consuming queries, query-time histograms, checkpoint activity, autovacuum/autoanalyze timing, lock-wait stats, per-db/user/client connection and session-duration stats, temp-file usage, error-class breakdowns, DML pie charts, and dedicated PgBouncer throughput/pool sections. Supports incremental mode (`-I`, tracks last-parsed byte offset in a state file) and binary intermediate output for cumulative merging across runs. (Source: github.com/darold/pgbadger, README.)

kbdiag already has a log-file-based command (`lib/cmd_logs.sh` — "log file analysis (slow queries, errors, fatals)"), i.e. a narrow slice of pgBadger's log-parsing space, without pgBadger's histogram/HTML/incremental-state machinery.

### 1.4 pgmetrics (github.com/rapidloop/pgmetrics, pgmetrics.io)

Explicitly a **stateless, one-shot CLI collector** (their own description) — connects, gathers a large struct of point-in-time facts (system stats, DB/table/index size and bloat, replication state, backends/locks, autovacuum/vacuum progress, WAL, sequences, roles, tablespaces, triggers, `pg_stat_statements`, PgBouncer/Pgpool ecosystem stats — 350+ data points across RDS/Aurora/GCP-SQL/on-prem), and dumps a single JSON or text report. No daemon, no persisted repository — closest of the five in spirit to kbdiag's own architecture. (Source: pgmetrics.io homepage / github.com/rapidloop/pgmetrics.)

kbdiag's `snapshot` command ("pack volatile incident state into one tarball for later analysis or a vendor ticket. Collection only, no judgment" — `lib/cmd_snapshot.sh`) occupies the same niche as pgmetrics' one-shot dump, but as a raw-evidence tarball rather than a single structured JSON model.

### 1.5 pganalyze (pganalyze.com — commercial SaaS)

Runs a lightweight collector agent that continuously ships stats to a hosted backend; the backend does the heavy analysis and keeps history, so pganalyze itself is not a local stateless tool — it's the one reference tool that fully embraces a persistent-repository model (cloud-side, not agent-side). Capability highlights relevant to gap analysis:
- **Log Insights**: parses Postgres logs for errors/slow queries, similar territory to pgBadger. (pganalyze.com/log-insights)
- **Index Advisor**: workload-driven — uses accumulated query-history/workload data plus simulated ("hypothetical") indexes (the HypoPG-style what-if mechanism) to recommend new indexes without actually building them; also flags unused indexes. Explicitly needs ongoing workload/query history, not a single point-in-time snapshot. (pganalyze.com/postgres-index-advisor; corroborated via web search of pganalyze.com/postgres-indexing-engine)
- **Vacuum Advisor / Schema Statistics / EXPLAIN visualization / connection & lock monitoring** round out the product, all built on the same continuously-collected-history model.

The HypoPG-style hypothetical-index mechanism is the one piece of pganalyze's stack that does **not** require persistent history — it's a per-session "what if this index existed" cost estimate, computed live. That's relevant to section 4 below.

## 3. KingbaseES rolling-metric-history opportunity (deep dive)

This is the most promising lead within the architectural constraint, because — unlike AWR — KingbaseES ships **two separate, database-side, non-kbdiag-maintained** history mechanisms that between them cover both `ora`'s ASH angle and its AWR angle, without kbdiag persisting a single byte.

### 3.1 `track_real_stats` → `sys_stat_sysmetric` / `sys_stat_sysmetric_history` (the lightweight rolling buffer)

This is the exact mechanism the prior spot-check found empty. KingbaseES's Oracle-compatibility layer ships `v$sysmetric`/`v$sysmetric_history` (sys-prefixed: `sys_stat_sysmetric`, `sys_stat_sysmetric_history`), modeled directly on Oracle's `V$SYSMETRIC_HISTORY` (docs.oracle.com/en/database/oracle/oracle-database/19/refrn/V-SYSMETRIC_HISTORY.html — the same view `ora` doesn't even bother querying directly, because ASH is richer). KingbaseES's own docs confirm:

- Population is gated by a GUC, **`track_real_stats`**, documented as controlling "实时统计的开启（on）/关闭（off），默认为关闭" (real-time-stats on/off, **default off**) — source: help.kingbase.com.cn/v9.3.11/development/application-develop-guide/internal_views/oracle_views/dynamic_performance/vmetric_history.html and .../vsysmetric.html. This confirms the spot-check hypothesis exactly: the views exist, are schema-complete, but sit at zero rows until this GUC is flipped on.
- `sys_stat_sysmetric_history` is a rolling window (short/long duration buckets, mirroring Oracle's "Long/Short Duration" split in `V$SYSMETRIC_HISTORY`) — a bounded circular buffer, not unbounded growth, so enabling it has a fixed, small memory footprint rather than an open-ended one.
- **Open item, not yet verified**: whether `track_real_stats` is `SIGHUP`-reloadable or requires a full restart (`postmaster`-context). This determines how disruptive "please enable this" is as an operational ask. Verify empirically on the test VMs (`kbdiag params track_real_stats` or `SHOW context` via `sys_settings`) before writing any spec that depends on it.

If enabled, this alone gives kbdiag a genuinely stateless way to answer "what did CPU/wait-class load look like over the last N minutes" — a single `SELECT ... FROM sys_stat_sysmetric_history WHERE ...` query, formatted by a new or extended `查`-tier command, no kbdiag-side sampling loop required.

### 3.2 `sys_kwr` (Kingbase Workload Repository) — the bigger find

Researching the sysmetric angle surfaced something materially more valuable that the task background didn't flag: KingbaseES ships an **extension** called `sys_kwr` that is architecturally a genuine Oracle-AWR-and-ASH equivalent, living entirely inside the KingbaseES instance:

- **What it is**: a background-process-driven snapshot repository. Per official docs (help.kingbase.com.cn/v9.3.11/admin/reference/ref-extended-plug-in/sys_kwr.html): it must be added to `shared_preload_libraries` (alongside e.g. `plmysql, sys_kwr, sys_stat_statements`) and requires `CREATE EXTENSION`. Once loaded, a background collector process takes a snapshot **once per hour by default** (interval tunable via `sys_kwr.interval`) and stores it in `perf.kwr_snapshots`. Snapshots can also be forced manually via `perf.create_snapshot()`.
- **KSH (Kingbase Session History) is bundled in**: controlled by `sys_kwr.collect_ksh` (documented default **on** once the extension itself is enabled). This is a direct Oracle-ASH analog — per the docs, it "以每秒采样的方式进行会话和数据收集，并将采集数据放入共享内存中，采集的数据主要包括：会话、应用、等待事件、命令类型、QueryId等" (samples session/application/wait-event/command-type/QueryId data every second into shared memory). Earlier KingbaseES versions (v8.6.x) shipped this as a standalone `sys_ksh` extension (help.kingbase.com.cn/v8.6.7.12/development/sql-plsql/ref-extended-plug-in/sys_ksh.html — "主要功能是会话历史的分析，并针对报告呈现的性能瓶颈进行优化", i.e. "primary function is session-history analysis, targeted at surfacing performance bottlenecks in reports") before being folded into `sys_kwr`.
- **Report generation is built in**: `perf.kwr_report(start_snap_id, end_snap_id)` and `perf.kwr_report_to_file(...)` produce an AWR-style diff report between two snapshots — the exact shape of `ora`'s `awr_*` commands, generated entirely DB-side.
- **Retention/config**: overall master switch is `sys_kwr.enable` (docs note version-dependent availability — confirm exact GUC names against the target instance's version before depending on them); retention is time-bounded (docs reference a default multi-day retention window, keep this as "verify on target version" rather than a hard number pulled from search snippets).
- **Crucially, this is NOT contradicting the task's "no persistent AWR-repository equivalent" finding** — that finding was about KingbaseES's *native, always-present* catalog (no `dba_hist_*`-equivalent tables exist out of the box). `sys_kwr` is an optional, separately-installed extension requiring a `shared_preload_libraries` edit and instance restart to add. It is very plausibly **not installed** on a given customer's instance (including the test VMs, unconfirmed) — so the opportunity here is conditional: *if present*, kbdiag gets AWR+ASH for free, DB-side; *if absent*, kbdiag is exactly where it is today.

### 3.3 What this means architecturally

Both mechanisms satisfy Option C perfectly: kbdiag would add a **detection + read-only query** layer, never a collector. Concretely:
1. A `看`-tier or `查`-tier check for "is `track_real_stats` on" / "is `sys_kwr` extension installed and collecting" — cheap, single-query, degrades gracefully to "not available, enable X to unlock historical trend data" (consistent with kbdiag's existing repmgr-absent degrade pattern).
2. If `sys_kwr` is present: a thin wrapper command that calls `perf.kwr_report()` between the two most recent snapshots (or user-specified snapshot IDs) and reformats/greps the output into kbdiag's existing verdict/evidence idiom — this is close to a `report`-tier feature, not a new subsystem.
3. If only `track_real_stats`/`sys_stat_sysmetric_history` is present (lighter-weight, no extension install needed, just a GUC): a `查`-tier "trend" view over the rolling buffer — smaller scope, smaller payoff, but zero-install (`sys_kwr` needs a restart + preload edit; the GUC does not, modulo the open reload-context question in §3.1).

Both are strictly better fits for kbdiag's constraints than anything in pg_profile/pgBadger's model, because the "repository" already exists on the DB side when present — kbdiag stays a pure client.

## 4. Prioritized shortlist (for follow-up planning, not a spec)

1. **Detect + surface `sys_kwr` when present.** Highest ceiling: turns on an AWR+ASH-equivalent diff report for free. Start with a detection check (extension installed? collecting? snapshot count/age?) before deciding how deep the wrapper goes. Needs a test VM with `sys_kwr` actually installed to validate output shape — unconfirmed on current test nodes.
2. **Detect + surface `track_real_stats`/`sys_stat_sysmetric_history` as a fallback/lighter path.** Lower ceiling than `sys_kwr` but zero-install (GUC only, if SIGHUP-reloadable — verify first). Good match for the existing `perf`/`stat`/`wait` command family as a "trend" subcommand.
3. **HypoPG-style what-if index advisor**, replacing/extending `idx missing`'s current FK-only heuristic with workload-driven simulation (à la pganalyze's index advisor), sourced from kbdiag's already-collected `stmt` data instead of continuous history. Verify `hypopg` (or KingbaseES equivalent) extension availability first — if absent, this drops out entirely.
4. **Log-histogram add-on to `logs`** (query-time buckets, error-class breakdown, DML-mix counts) — a narrow, explicitly-scoped slice of pgBadger's report, text/JSON output only (no HTML/charts, staying inside Option C). Cheap in pure shell (`awk` timing buckets on existing log-scan pass).
5. **Tighten `snapshot` toward a pgmetrics-style single structured JSON document** rather than a raw evidence tarball — smaller, more mergeable with `--json` global output convention already used elsewhere in kbdiag. Low novelty, mostly a consistency/polish item.
6. *(One-line mention only, out of scope per Option C)*: a pg_profile-style kbdiag-maintained metrics repository, or a pgBadger-style rich HTML report generator, remain a separate future-roadmap item if the architecture decision is ever revisited.
